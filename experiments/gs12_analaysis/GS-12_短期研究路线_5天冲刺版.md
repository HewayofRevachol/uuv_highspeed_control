## 2. 固定实验对象与可改参数

**主实验固定**：15 m/s、`PlantConfig(elevator=.9, rudder=.9, order="second_all")`，真实植物、配平、初态、参考、数值积分、命令盒约束、`dt=.1 s`、`N=35` 在配对运行中一致。C4/C5 只切换**预测器**：C4 `(model_gain=1, model_tau=1)`；C5 `(.85, 2)`。扫描权重时先固定 C4 预测器；C5 作为已知的模型偏置参照，不能将它与改权重的效果混为一因。

`CondensedActuatorMPC._one()` 当前直接构造以下非零代价项：

```text
state_weight = [3, 3, 3, pitch_weight(默认100), yaw_weight(默认30), 5, 5, 5]
input_weight = [0.15, 0.08, 0.08] × N
rate_weight  = [1.8, 0.35, 0.35] × N
```

`state_weight[2]` 对应深度跟踪，`rate_weight` 每个控制阶段的后两项对应双舵**归一化命令变化**惩罚。首轮仅引入两个正倍率：`a_D` 缩放 `state_weight[2]=3`，`a_Δδ` 将 `np.tile([1.8, 0.35, 0.35], N)` 改为 `np.tile([1.8, 0.35*a_Δδ, 0.35*a_Δδ], N)`，作用于**全部 N 个阶段**，不能只改扁平数组的 `[1:3]`。保留已有双舵命令量惩罚 `0.08`、pitch/yaw 权重、终端阶段 `2.5` 倍因子、硬约束和 OSQP 设置。`attitude_pitch_weight` 已有构造参数，但它**不是深度跟踪权重**，且已有单轴开发实验显示单纯加大 pitch 权重可能明显变差，故不作为本轮动作。

**最小代码改动**：在 `CondensedActuatorMPC` 增加默认均为 `1.0` 的 `depth_weight_scale`、`rudder_rate_weight_scale` 与一个校验有限正值的 setter；`_one()` 仅在构造 `state_weight[2]` 与双舵逐阶段 `rate_weight` 时读取它们。不要顺手重写 QP 或引入通用权重矩阵。静态倍率可由现有 `plant_harness.run_closed_loop(..., mpc_setup=...)` 注入。动态倍率需要在每次 `mpc.solve` **之前**调用 setter；现有 `mpc_setup` 只运行一次，因此在新目录建立薄 runner，复用旧 `plant_harness.Plant`、`diagnostic_values` 和参考函数，单独实现带 `before_solve` 的闭环循环。不要直接改历史 `frequency_extension_src/plant_harness.py` 或覆盖 `frequency_extension/` 数据；新 runner 的 `(1,1)` 轨迹必须与旧 harness 对齐。

## 3. 接手 agent 的接口契约

按以下顺序交付，每一步的产物是下一步输入。建议新增文件名是实施目标，当前尚不存在。

| 顺序 | 修改/新增位置 | 具体职责 | 最小验收 |
|---|---|---|---|
| 1 | `aav_mpc/condensed_mpc.py` | 增加两个倍率和 setter；只改两处代价系数 | `(1,1)` 的原命令/计划/QP 状态一致；两个倍率各自改变对应 QP 项 |
| 2 | `experiments/gs12_weight_route/reference_tasks.py` | 用历史 `signal()` 生成单频参考；用光滑包络生成混合参考及其解析导数，输出 `[N,E,D,pitch,yaw,VN,VE,VD]` | 数值差分检查 `dN/dt=VN`、`dE/dt=VE`、`dD/dt=VD`；参考与导数在频段切换处连续 |
| 3 | `experiments/gs12_weight_route/runner_core.py` | 复用 `Plant` 与诊断函数；每个任务新建植物/MPC，固定初态与 warm start；`before_solve` 更新倍率；计时 `mpc.solve` | `(1,1)`、同参考的状态/命令/QP 序列与旧 harness 在数值容差内一致 |
| 4 | `experiments/gs12_weight_route/run_weight_route.py` | 读取冻结协议，生成任务清单，运行单条/整批，保存每条 JSON 与 NPZ；支持 `--stage`、`--workers`、`--out` | 1 worker 与多 worker 对相同任务得到相同结果；任务数、状态与日志数相符 |
| 5 | `experiments/gs12_weight_route/analyze_weight_route.py` | 统一窗口、共同前缀、完成/早停、饱和、QP、代价与配对报表 | 不同 Q/R 均用同一外部 `J_track` 评分；缺失任务不被静默排除 |
| 6 | `experiments/gs12_weight_route/spectral_rule.py` | 只在节点 B 显示不同频带优选参数后实现 FFT 特征与倍率插值 | 用同一参考计划计算因果可用的特征；固定端点与规则的预览条件一致 |

任务记录的最小主键为 `(protocol_sha256, split, task_id, controller_id, weight_policy_id, amplitude, phase_id)`，由此生成唯一 `run_id`。`tasks.jsonl` 先锁定参考任务；每批开始前再冻结该批要执行的控制器/策略列表。任务参数只传 JSON 可序列化的标量/字符串给 worker；在 worker 内先设置 `GS12_REPO`，再导入旧 harness 并构造参考函数、MPC 与植物。每条运行写自己的 `runs/<run_id>.json` 和 `traces/<run_id>.npz`，分析器只读已完成文件。参考生成、权重策略、植物和预测器是四个独立字段，避免 `C5` 同时被误当成植物与控制器。

**建议 CLI 合同（待实现，不是现有命令）**：`prepare --out ...` 冻结协议和清单；`pilot --workers 1|2|4 --out ...` 测吞吐；`scan --workers W --out ...`；`dev-rule --workers W --out ...`；`test-locked --workers W --out ...`；`analyze --out ...`。运行时允许 `--start-index/--stop-index` 执行清单连续分片，但不改变任务定义。未实现某阶段前，不把以上命令写成“已可运行”。

**运行循环骨架（伪代码，函数名需按实际实现）**：

```python
def run_one(job):
    model, plant, mpc, ref_grid, policy = build_from_frozen_job(job)
    for k in range(job.control_steps):                 # 轨迹内部必须顺序执行
        state = model.tensor(plant.controller_state())[None]
        preview = model.tensor(ref_grid.mpc_slice(k, horizon=35))[None]
        scales = policy.scales(k, state, ref_grid)     # 静态策略返回常数
        mpc.set_tracking_weight_scales(*scales)
        started = perf_counter()
        command, qp_ok = mpc.solve(state, preview)
        solve_seconds.append(perf_counter() - started)
        physical_command = command[0].numpy()
        for j in range(5):                            # 每周期 5×0.02 s 植物步
            plant.step(physical_command)
            log_substep(k, j, plant, ref_grid)
            if diagnostic_limit_hit():
                return save_early_stop(job)
    return save_complete(job)
```

这里的 `policy`、`ref_grid` 和记录函数由新 runner 实现；`mpc_slice(k)` 必须取 `t=(k+1)…(k+35)` 的 0.1 s 未来参考。初始化照 `plant_harness.run_closed_loop`：`Plant.controller_state()` 的 22 维状态由艇体 10 维、归一化实际执行器 3 维和命令队列 9 维组成；用植物配平命令初始化 `mpc.previous` 与整条 `mpc.plan`，预测器用 `ActuatorAwareCpuDynamics(.1, model_gain, model_tau)`。诊断边界按每个 0.02 s 子步判定，触限的首子步保留在记录中。逐步对齐检查通过后再用批量模式。worker 只返回 `run_id/status/wall_s` 等小对象，完整轨迹直接写本任务 NPZ，避免进程间传大数组。

## 4. 执行节点与验收

### 节点 A：冻结协议与验证权重接线

1. 完成第 3 节的基础代码后，生成 `protocol.json` 和 `tasks.jsonl`，将 `dev_scan`、`dev_rule`、`test_locked` 三组**参考任务一次冻结**。协议记录植物/预测器、权重索引、参考公式及相位、初态、幅值、窗口、质量规则、基础源码 SHA-256、Git commit、Python/依赖版本；每条任务记录 `task_id`、阶段、频率/相位和时长。候选与可选频谱规则尚未确定，其方法清单在各批运行前另行冻结；后加的 `spectral_rule.py` 单独记录策略代码哈希，不回写已冻结任务。此时不运行锁定测试，也不让扫描结果反向修改其任务。
2. 对同一状态、35 步参考和相同 warm start，分别用原控制器和新增 `(a_D,a_Δδ)=(1,1)` 求解；核对首命令、完整计划与 QP 状态。单独变动 `a_D` 与 `a_Δδ`，用一次性诊断钩子检查 Hessian/gradient 中对应项的变化；若约束掩盖命令差异，仍须证明 QP 目标已变化。此诊断钩子只用于接线验证，不逐步保存整张 Hessian。
3. 用旧 harness 与新 runner 各跑同一条短 C4 轨迹，比对每周期命令、10 维艇体状态、实际执行器、诊断值及早停时间。新 runner 逐次记录 `mpc.solve` 墙钟时间；旧 harness 只有整条轨迹的墙钟时间。核对零倍率改动（`1,1`）后才允许进入批量扫描。
4. 为当前机器测吞吐：同一组 4 条完整 64 s 任务分别以 1、2、4 worker 运行，使用独立 `pilot_w1/w2/w4` 输出目录。记录整批墙钟时间、每条运行时间、峰值 worker RSS 和失败/早停数；只对**同样任务数与任务内容**比较吞吐。选实测吞吐最高且内存可承受的 worker 数。若 4 worker 对 2 worker 提速明显，且后续确定要跑 39 条长协议，可再用同一组 8 条任务比较 4 与 8 worker；只有预计节省的长协议时间大于这轮额外 pilot 成本才做。不要因本机看到 16 个可用 CPU 就直接开 16 worker。

**通过条件**：倍率为 1 时重现原控制器，倍率变化进入 QP，短闭环日志完整，吞吐测试确定后续 worker 数。任一接线或配对条件未满足，先修代码，不将“权重无收益”解释为研究结果。

### 节点 B：固定权重小网格，找出是否存在频带取舍

1. 开发网格固定为 `a_D × a_Δδ = {0.7,1.0,1.4}²`，共 9 组，包含原始 `(1,1)`。`dev_scan` 先只含 15 m/s C4 植物、C4 预测器、深度轴 `k=8` 与 `k=32`，即 18 条候选轨迹；另跑两条相同参考的 C5 参照，共 20 条。按节点 A 的 worker 数整批并行，**一条闭环轨迹是一个并行任务**，轨迹内部 0.1 s 控制循环保持串行，保证 warm start 因果顺序。容量允许时再扩到东向/速度轴或 `k=16/24`，扩展前冻结补充清单并标为开发集。
2. 快筛采用研究用单频短协议：通过现有 `signal(t, [k], [phase], amplitude)` 构造单频位置/速度解析一致的 8 维参考；现有 `make_reference()` 固定选择整组 B1–B4 频线，不能直接作为单频入口。总长 64 s，前 16 s 使用与历史协议一致的平滑包络，主评价窗口 `32–64 s`；`ω_k=2πk/64`。在该窗口 `k=8` 有 4 个整周期、`k=32` 有 16 个整周期。快筛只计算时域任务代价及单频复响应，**不标为历史 256 s 多正弦矩阵复现**。
3. 每组保存三个归一化误差通道的 RMSE/峰值、统一 `J_track`、命令及实际执行器饱和比例、最大归一化命令变化、诊断边界首次触发时间、QP 失败数与每步求解耗时。输出 9×2 配对表和权重热图；分析时按 `tasks.jsonl` 左连接运行记录，任何缺项显示为缺项，不参与排名。
4. 先排除新增早停或 QP 失败的组合，再按两个开发任务的等权相对改进选一个整体最优；若高、低频的优选区域不同，再保留一个有代表性的频带端点。只允许在 `dev_scan` 上定候选，候选 ID 和选择理由写入 `selection.json`。若没有任何组合优于 `(1,1)`，记录“开发集未发现正向配置”及实际诊断证据，再转节点 E；这仍是可汇报的研究结果。

**计算止损**：以试跑实测吞吐估计 20 条扫描批次和后续确认批次墙钟时间；先保留足够预算完成冻结测试，再决定扩轴/扩频。若批次超预算，改跑预先列出的 5 个十字形配置 `[(1,1),(.7,1),(1.4,1),(1,.7),(1,1.4)] × 2`，并在 `selection.json` 标注实际搜索空间；不在首轮上来就做全 32 频点或更大网格。

### 节点 C：开发混合任务与固定候选复核

`dev_rule` 预先定义两条 64 s 的“低→高→低”混合参考，用来检查固定候选及设定规则参数；`test_locked` 预先定义但此时**不运行**。混合参考先取 `k=8`、`k=32` 的东向/深度波形，用两次 2 s 光滑过渡在约 20 s 与 40 s 切换高频比例；`E_ref=8z_E`、`D_ref=20+5z_D`、`VE_ref=8ẋz_E`、`VD_ref=5ẋz_D`，`VN_ref=15`、`N_ref=15t`，pitch/yaw 由参考速度方向计算。切换包络的导数必须进入 `VE_ref/VD_ref`，不能直接拼接两个已有参考造成速度跳变。两条开发任务使用不同的固定相位。

把 B 中冻结的 1–2 个固定候选与原始 C4、C5 在这两条 `dev_rule` 任务上配对运行，共 6–8 条 64 s 轨迹；整批按任务并行。此时可以因 `dev_rule` 表现否决候选或确定规则阈值，**不能重新标称它为独立测试收益**。如果 B 中频带最优相同或 C 中两个候选在混合任务无明显取舍，就保持最佳固定权重，跳过动态规则，直接在 `test_locked` 评估静态方法。

主指标预先定义为共同评价窗口内三个工程归一化误差的 MSE 和：

\[
J_{\mathrm{track}}=\operatorname{mean}\left[\left(\frac{E_\mathrm{ref}-E}{8}\right)^2+
\left(\frac{D_\mathrm{ref}-D}{5}\right)^2+
\left(\frac{V_{N,\mathrm{ref}}-V_N}{2}\right)^2\right].
\]

同一配置发生早停时，不能用短轨迹平均值与完整轨迹直接排名：先报告完成/越界及时间，再在**该任务所有方法共同前缀**计算跟踪指标；完整任务另报全程指标。新增诊断边界触发、QP 失败或明显饱和/命令尖峰不能被较低 `J_track` 掩盖。对锁定测试的每个任务分别计算 `J_track`，再以任务等权平均 `\bar J=(1/m)Σ_i J_i`；静态候选的严格工程晋级条件是 `100×(\bar J_C4-\bar J_new)/\bar J_C4≥5%`、每个任务的 `J_i,new≤J_i,C4`、无新增失败。逐任务同时列出 `100×(J_i,C4-J_i,new)/J_i,C4`。**平均代价的相对变化**与**逐任务相对变化的平均**是不同量，报告中不要混用；5% 是预设工程门槛，不是统计显著性阈值。

`test_locked` 的三条最小任务是：`k=6` 深度轴（新相位）、`k=30` 东向轴（新相位）、一条切换时刻和相位均不同于 `dev_rule` 的混合轨迹。测试清单与相位在节点 A 冻结；只在固定权重及可选频谱规则均已冻结后批量运行 C4、C5、最佳固定候选与规则。没有规则时为 9 条轨迹；有规则时为 12 条；保留第二固定候选时分别再加 3 条。所有方法配对同一任务，分析器必须检查每个 `task_id` 的方法集合完整。

| 层次 | 根据冻结结果可以汇报什么 | 能否称新控制性能改进 |
|---|---|---|
| **达到正式目标** | `test_locked` 相对 C4 的平均 `J_track` 降低至少 5%，每个任务均不恶化，且无新增失败；并列出各通道 RMSE、约束和 QP 状态 | 可以，但仅限已测植物、任务、速度和协议；若只有固定权重通过，只归因于固定调参 |
| **初步正向结果** | 开发集有改善；或冻结测试中部分任务改善，但未同时满足平均幅度、逐任务不恶化及无新增失败的全部条件 | 可称“开发集局部收益”或“部分留出任务改善”，不能称普遍有效或完成正式晋级 |
| **负结果但形成诊断** | 已证明权重改变 QP，却未获得可靠任务收益；结合记录指出约束激活、预测模型失配等**实际观察到的**限制及下一步可检验假设 | 不能称控制性能改进，但可以汇报机制诊断和后续路线 |

这是**成果表述分级**，不改变预先冻结的 5% 严格工程门槛。不能为了得到醒目的百分比，只挑一条表现最好的轨迹或在测试后改主指标；逐任务结果、早停、失败和退化须一起呈现。

### 节点 D：只有静态频带取舍成立时，测试频谱连续规则

1. 使用**部署时可获得的未来参考**计算特征。现有 MPC 每次只消费 35 个 `0.1 s` 参考点，即 3.5 s；16/32 s 的频谱观察窗需要额外从同一外生参考计划取未来段，不能声称它已由 MPC 接口提供。首先在协议中明确允许 16 s 参考计划预览；若部署仅允许 3.5 s，则改用 3.5 s 差分/短窗特征，并将低频分辨率不足列为限制。不要在锁定测试后改预览长度。
2. 每 `0.5 s` 从当前时刻向前取 16 s 的参考样本；对东向/深度/北向速度的**偏离直航基线部分**分别按 `[8,5,2]` 归一化，去趋势、加 Hann 窗，用 `np.fft.rfft` 和 `np.fft.rfftfreq` 把 Hz 转成 rad/s。定义 `E_total=Σ_{f>0,通道}|FFT|²/n²`，`ρ_high=Σ_{ω≥2.2,通道}|FFT|² / Σ_{f>0,通道}|FFT|²`；记录 `E_total`、`ρ_high` 与当前航速。总能量过小时按下一步的预设行为处理。当前任务为时间参数化参考，不额外加入空间频率转换；若未来任务改成弧长参考，再另立协议。
3. 初始规则直接设 `β=clip((ρ_high-0.25)/0.50,0,1)`，`a=(1-β)a_low+βa_high`；归一化非直流总能量低于预设 `1e-8` 时保持上次倍率（初次为最佳固定倍率）。每 `0.5 s` 更新一次两倍率，任一倍率每次变化最多 `0.1`，MPC 仍每 `0.1 s` 解一次，两个更新之间保持倍率不变。`ρ_high`、能量定义、端点和速率限制都写入协议；若在 `dev_rule` 修改这些值，记录版本与理由，进入 `test_locked` 前冻结。每步保存频谱特征、倍率、命令变化和 QP 状态。这个策略称为**频谱规则**。
4. 在 `dev_rule` 调定规则后冻结阈值、端点、预览长度和代码哈希，再与原始 C4、C5、最佳固定权重一起进入 `test_locked`。四者使用同一植物、同一任务和同样可用的参考计划；固定权重不因能预览更远而改变。仅当锁定测试显示规则优于最佳固定值时，再在**另一个预留诊断任务**做“冻结倍率”和“去掉频谱特征”两种消融，不用锁定测试反复调规则。

**规则的独立价值**：在 `test_locked` 三条任务上，以相同的 `\bar J` 定义比较规则与最佳固定权重；规则平均至少降低 5%、逐任务不恶化，且不新增失败、明显饱和或命令尖峰，才称频谱调度达到预设晋级门槛。规则即使相对 C4 达标，若未赢最佳固定权重，也只能把可证实的收益归于静态调参；规则的独立收益未证实。

### 锁定测试通过后的可选长协议复核

锁定测试出现正式达标或值得解释的局部正向信号后，可按计算预算优先对固定候选与 C4/C5 重测 15 m/s 的 `k=8/32` 单频；需要正式 3×3 B1/B4 矩阵时，再按历史 `256 s`、W2/W3 复数平均、主幅 `0.006`、半幅 `0.003` 和同控制器零激励基线执行。三种控制器、两个频带、三轴、两幅值加各自零基线至少 **39 条 256 s 轨迹**；第二固定候选再加 13 条。现有 C4 同类 256 s 完整轨迹的记录墙钟时间中位数约 `106 s`（33 条样本），按此量级 39 条串行约 69 分钟，尚未计并行争用、I/O 与分析。因此先用吞吐实测预算决定做单频还是完整矩阵，不默认完整重测。新矩阵分析器需沿用历史窗口/质量定义，不能直接把现有只认 C0–C5 的 `analyze` 入口当成新权重分析器；动态规则只报告条件化经验响应，不套用固定 LTI FRF 解释。

### 节点 E：结果不支持权重路线时的转向

- **权重影响 QP 但没有稳健收益**：优先沿现有 C5 `.85/2.0` 预测偏置做少量模型参数扫描或分通道预测器比较；`experiments/gs12_analaysis/frequency_extension_src/improved_controller.py` 与 `experiments/gs12_gate/` 提供已有结构/门控实现。仍固定真实植物并做配对留出，不把模型调整归因于 Q/R。
- **静态收益成立而动态无独立收益**：保留最佳固定权重，停止扩展频谱网络与 RL；先检查更广任务和速度下是否保持收益。
- **只有频谱风险相关、没有控制收益**：利用现有 `frequency_extension/matrices/all_matrices.json` 构造 `||T(jω_k)z_k||²` 风险图，与留出轨迹误差对照。注明这是诊断/特征实验，不是控制改进。
- **确有上下文相关且规则优于固定**：再考虑把同一观测/动作/外部评价接口接入现有 `gs12_gate` 训练框架；新策略仍需强固定基线、显式规则及冻结测试集对照。现有 PPO `dev_quick` 未晋级，不构成扩训理由。

## 5. 批量并行与计算预算

**任务粒度**：任务清单在主进程生成并检查 `run_id` 唯一；`ProcessPoolExecutor(max_workers=W)` 把每条闭环轨迹分给一个 worker。worker 独立创建 MPC、植物和参考，按时间顺序运行该轨迹，写该 `run_id` 专属文件，只返回少量元数据。主进程用 `as_completed` 收集结果、串行更新 `manifest.json` 与进度；分析/绘图在批次结束后做。现有 10 状态 runner 已采用这一模式，可参考 `experiments/gs12_10state_experiment/src/run_experiment.py:run_stage`，但要为本路线单独构造任务和输出格式。**不要**把一个 MPC 轨迹的时间步分给多个 worker：状态与 warm start 依赖前一步。

**线程与内存**：在 Python 导入 NumPy/Torch/CasADi 前，由 launcher 设置 `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1`；每个 worker 再设 `torch.set_num_threads(1)`。不要同时手动启动多个批次抢同一批 CPU。以 pilot 的批次墙钟时间、吞吐 `任务数/墙钟秒`、每 worker 峰值 RSS 选择 `W=1/2/4`；仅在长协议节省时间预计超过额外 pilot 成本时测试 `W=8`。10 状态实验曾测到 4 worker 吞吐约 819 条/小时、1 worker 约 523 条/小时，但那是另一预测器与任务，**只能作为需要实测的理由，不能直接用于本路线预算**。

**参考计算**：每个 worker 对确定性参考预生成 0.02 s 植物采样网格和 0.1 s MPC/频谱预览网格，覆盖任务终点后额外 16 s；循环内按整数索引切片，避免每步反复求三角函数。64 s 的 0.02 s 八维参考约 3200×8 个数，内存量级很小。首次实现先用旧在线参考函数核对数值和完整 `(1,1)` 轨迹，再开启预计算；若计时表明节省很小，保持较简单的在线版本即可。FFT 每 0.5 s 计算一次，不在每个 0.1 s MPC 步重复计算；预览特征只基于计划参考，不读取未来真实植物状态。

| 批次 | 任务数下限 | 并行时机 | 是否必须 |
|---|---:|---|---|
| 接线/轨迹一致性 | 1–2 | 串行，便于逐步比对 | 必须 |
| 吞吐 pilot | 4 条 × 1/2/4 worker = 12 条执行 | 三组顺序运行，每组内部并行 | 必须，选实际 worker 数 |
| `dev_scan` | 20；预算不足用 12（5 个十字配置 × 2 + 2 条 C5） | 同一协议批量并行 | 必须 |
| `dev_rule` | 6–8 | 固定候选确定后批量并行 | 有静态候选时 |
| `test_locked` | 9（无规则）或 12（有规则） | 所有策略冻结后批量并行 | 有静态候选时必须；纯负扫描可止步 |
| 长协议 B1/B4 | 至少 39 | 锁定测试通过且预算允许后并行 | 可选 |

从 pilot 计算 `预计批次墙钟秒 ≈ 任务数 / 实测每秒吞吐`；长协议另用一条 256 s 任务实测，不能把 64 s 耗时简单乘 4。每批开跑前输出任务数、worker 数、预计耗时与剩余预算；若预计超预算，先删**可选**扩轴、额外相位和长协议，不删配对基线或有候选时的锁定测试。即使并行，逐条仍保存 `solve_p50/p95/p99_ms`；用于单艇实时性判断的延迟以 **1 worker** 试跑为准，4/8 worker 的延迟含资源争用，只用于估算并行吞吐。

**并行写入的实际冲突**：多个 worker 同时读改写一个 `manifest.json` 会丢记录；这是本批次会遇到的具体共享写入，且由主进程汇总即可消除，改动很小。因此 worker 只写各自唯一文件，manifest 由父进程写。运行前检查 `run_id` 唯一；重复 ID 会覆盖同名轨迹，属于任务生成的直接错误。除此之外，不为想象中的跨机器并发、恶意输入或极罕见文件竞争引入锁服务、事务数据库、分布式调度器或通用安全框架。若后续确有此类需求，接手 agent 先向用户说明**具体失败模式、发生可能性、实现/维护成本**并取得同意，再扩大范围；不能悄悄增加理论性健壮化工作。

每行指标至少保留 `run_id,task_id,plant,controller,weight_policy,ref_task,split,speed_mps,frequency_k,amplitude,phase_id,a_depth,a_rudder_rate,protocol_sha256,window_start_s,window_end_s,completion,first_violation_time_s,J_track,rmse_E,rmse_D,rmse_V,command_saturation,actual_saturation,qp_failures,solve_p95_ms,wall_s,source_sha256`。`plant=C4, controller=C5` 是允许且必要的不同字段。NPZ 保存控制周期的参考/输出/命令/倍率/QP 状态与植物子步状态/实际执行器/诊断值；JSON 保存参数、质量状态、首触限时间及 trace 哈希。任何失败或早停都写明状态，不用成功样本数量掩盖。历史结果直接从 `frequency_extension/results.md`、`summary.json` 和 `matrices/all_matrices.json` 读取；改动生产 MPC 后，旧 `run_frequency_extension.py` 的 `prepare` 会发现仓库源码哈希变化，**不能再用原输出目录重新执行历史 `analyze` 命令**。新实验只写新目录。

最终汇报按“**历史证据 → 新权重接口与开发扫描 → 冻结留出结果 → 三层成果判断及下一步**”组织。图表将 `J_track`、相对 `J_track` 改进率和各通道 RMSE 分开列，标明开发集/锁定测试、评价窗口、完成/早停与失败数。`J_track` 是归一化误差的**平方和均值（MSE 类型）**；例如 `J_track` 降低 6%，即 `J_new/J_C4=0.94`，若仅对**同一个平方误差指标**取平方根，其降幅为 `1-√0.94≈3.05%`，不能据此说东向、深度或速度任一通道的 RMSE 也降低 6%。各通道 RMSE 必须从相应误差序列分别计算并列示。

历史 C4/C5 的 B4 约 32% 峰值下降只能标为既有结果。新结果同时报告完整/早停数、共同前缀指标、全部通道、约束、QP 状态和计算耗时；单条轨迹、单一频点或开发集最优不能称为普遍提升。确定性频点、窗口和子步不是独立随机样本；本路线也不提供实艇或鲁棒稳定性保证。
