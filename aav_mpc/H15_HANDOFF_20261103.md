## 恢复时先做什么

1. **先核对工作区。** 从仓库根目录运行下面的快速验证，读两份报告和对应 `run.json`。此前所有 H15 新文件与修改均未提交；两个已删除的 README 和未跟踪的 `docs/basline_experiment_plan.md` 是原有工作区状态，勿擅自恢复或覆盖。实验输出目录可能被 Git 忽略，交接时要连同 `outputs/experiments/mpc_h15_*` 保留。

   ```bash
   OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 /bin/python3 -m pytest -q \
     tests/unit/test_h15_experiment.py \
     tests/unit/test_aav_mpc_dynamics.py \
     tests/unit/test_recovery_mpcc.py
   git diff --check
   ```

2. **修正预测误差诊断口径。** 当前 condensed MPC 的 `states` 来自 RTI 线性化时的旧控制序列；`diagnose.py` 直接读其下一状态，不能无条件称为“已接受新命令的预测误差”。先加一个只针对首步的已接受命令重算与独立植物测试，再决定是否重跑必要的误差诊断。不要用旧逐周期 `prediction_1_*` 字段支持模型精度因果结论；已有离线命令重放证据另见详细报告。

3. **处理随机目标域可行性，限制运行时间。** 代表性失败种子的全未来扰动长窗搜索已在约五分钟内无候选，10 s 前缀搜索亦触发 60 s CPU 上限。恢复后优先缩短或分段优化，或使用其它能验证完整路径的 oracle；每次设明确时间上限，保存无解/超时状态，并把候选命令放回 `h15_oracle_command_replay.py` 的目标环境重放。只有完整、逐周期合规重放才是该种子的存在性证据。

4. **开发确定性修复再设新留出。** 重点是二阶执行器状态/响应估计、舵效估计、实际执行器和航速约束及求解失败回退。现有硬 RTI 在原测试耦合路径有 219 次回退，软 RTI 的预测俯仰松弛最高约 157°，二者不能直接定为安全基线。先用另行生成的开发几何少量配对种子筛查，固定方案后再冻结新的留出几何与种子；新方法至少与 OSQP N20、condensed N35/N40 同条件配对。

5. **最后单独测实时性与完成率。** 并行进程只用于正确性初筛。正式 CPU 控制周期 p50/p95/p99 必须无并行竞争重测，尤其对预测近似的 30 个并行筛查单元。只有跨几何和目标域重复、相对最强确定性 MPC 达到预设至少 10 个百分点的严格完成率改善、p95/p99 均低于 100 ms 且不靠明显降速时，才评估一个低维 RL 接口。当前尚未达到这个门槛。
